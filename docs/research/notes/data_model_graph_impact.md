## 1. Canonical model and provenance standards

### Takeaway
Use PROV-DM concepts (Entity / Activity / Agent, derivation, attribution) as the *vocabulary* for the evidence layer, and keep a plain relational schema; do not adopt an RDF/OWL stack. Existing products (Jama, Polarion, DataHub, Salesforce) each cover only part of the need: none gives per-edge OBSERVED/INFERRED/CONFIRMED status with cell-level evidence, so that is bespoke design. OpenLineage fits run/job/dataset lineage events, not requirement/config graphs.

### Cited Findings
- [DOC] PROV-O is a W3C Recommendation dated 30 April 2013 that expresses PROV-DM in OWL2; it is a lightweight ontology and, apart from five axioms, conforms to OWL-RL. Namespace http://www.w3.org/ns/prov#. — [W3C PROV-O REC (via search)](https://www.w3.org/TR/2013/REC-prov-o-20130430/)
- [DOC] PROV family: PROV-DM is the conceptual model; PROV-O, PROV-XML and PROV-N are serializations. Derivation reads "e2 was derived from e1"; generation links an entity to the activity that produced it (prov:wasGeneratedBy). — [PROV overview](https://www.w3.org/TR/prov-overview/Overview.html), [PROV-N REC](https://www.w3.org/TR/2013/REC-prov-n-20130430/)
- [DOC] OpenLineage's core entities are run, job and dataset; facets attach extensible context to each (run facets e.g. nominalTime, errorMessage, parent; job facets e.g. ownership, documentation, and a newer lineage facet carrying explicit data-flow edges; dataset facets e.g. schema, dataSource). Facets are versioned via `_schemaURL` and `_producer`; custom facets need a project-specific prefix. — [OpenLineage facets spec](https://openlineage.io/docs/spec/facets/), [object model](https://openlineage.io/docs/spec/object-model), [job facets](https://openlineage.io/docs/spec/facets/job-facets/)
- [DOC] DataHub's file-based lineage source accepts an optional `confidenceScore` (0 low to 1 high, default 1.0), also at column level via FineGrainedLineageConfig. The docs excerpt does not show it in the core UpstreamLineage aspect. — [DataHub file-based lineage](https://docs.datahub.com/docs/generated/ingestion/sources/file-based-lineage)
- [DOC] OpenMetadata generates column-level lineage with a Lineage Agent and lets users manually edit table and column lineage; I found no confidence field in the results. — [OpenMetadata column lineage](https://docs.open-metadata.org/how-to-guides/data-lineage/column)
- [DOC] Jama Connect "suspect links" flag downstream items when an upstream item changes; configurable per item-type field; reviewers use Compare Versions; suspect status is cleared individually or in bulk by a human. — [Jama blog](https://www.jamasoftware.com/blog/5-ways-jama-connect-makes-traceability-easy/)
- [DOC] Polarion has a global/per-project "auto-suspect" default marking new work-item links suspect. Per-field suspect rules not confirmed. — [Polarion admin guide](https://docs.plm.automation.siemens.com/content/polarion/20/help/en_US/user_and_administration_help/administrators_guide/configure_work_items/configure_work_item_linking.html)
- [DOC] Salesforce MetadataComponentDependency is labelled Beta: no GA guarantee, "can discontinue at any time", evaluation only. Tooling API: max 2000 records/query, reports excluded, limited filters, no OFFSET; Bulk API 2.0 up to 100,000 records. Community reports of gaps (public groups, reports). — [Salesforce docs](https://developer.salesforce.com/docs/atlas.en-us.api_tooling.meta/api_tooling/tooling_api_objects_metadatacomponentdependency.htm), [community thread](https://trailhead.salesforce.com/ko/trailblazer-community/groups/0F93A00000020VuSAI)

### Inferences
- [INFER] Map to PROV: source document/version = prov:Entity; ingestion/extraction run (parser version, model id, prompt hash) = prov:Activity; parser, LLM, reviewer = prov:Agent; extracted fact derived-from source span (wasDerivedFrom with locator). Store as relational tables with PROV-named columns; offer PROV-JSON/Turtle export only if an auditor asks. Avoids a triple store.
- [INFER] Evidence locator should be a typed value (doc_version_id, page, sheet, row, cell range, XPath/JSON pointer, char offsets, content hash) separate from the claim; one claim may have N evidence rows. Verification status belongs on the claim (entity/edge), with status transitions in an append-only review-event table. Enforce "AI never sets CONFIRMED" with a DB check/constraint tied to a human agent_id, not only application code.
- [INFER] Salesforce lesson: even a vendor dependency API is incomplete (beta, record caps, excluded types), so the product needs an explicit "coverage/unmodelled" concept rather than assuming completeness.
- [INFER] Jama-style suspect links suggest a useful review workflow: when a CONFIRMED node's source version changes, mark dependent confirmed edges "needs re-review" instead of silently keeping CONFIRMED.
- [INFER, unsourced background] Bitemporal modelling: keep valid time (when the config was effective in the tenant) separate from transaction/recorded time (when we ingested it). Environment snapshots are naturally immutable, versioned facts; model each snapshot as a snapshot_id with entities versioned by (entity_key, snapshot_id) rather than SCD-2 row mutation. SCD type 2 ranges are a poor fit when snapshots are the unit of truth. DCAT (dataset catalog vocabulary) is for dataset catalogs and adds little here.

### Gaps
- Could not fetch PROV-DM text, DCAT, or bitemporal/SCD references in this session; the bitemporal/SCD guidance is background knowledge, not cited.
- No evidence found that DataHub/OpenMetadata core models record per-edge verification status comparable to OBSERVED/INFERRED/CONFIRMED.

## 2. Graph storage options and scale

### Takeaway
Start with PostgreSQL adjacency tables (nodes, typed edges, evidence, review events) plus recursive CTEs with the CYCLE clause, with a bounded depth, and load the traversal sub-graph into an in-memory library only if needed. Likely scale (inference) is far below where dedicated graph DBs pay off. Avoid Kuzu (archived) and treat AGE and Neo4j licensing as risks rather than defaults.

### Cited Findings
- [DOC] Apache AGE: release 1.8.0 listed by EnterpriseDB as 11 Aug 2026 supporting PostgreSQL 18 only; 1.7.0.1 (20 Mar 2026) supported PG 17 and 18. Pigsty lists PG17/18 packages. Azure Database for PostgreSQL Flexible Server announced AGE GA (May 2026 post); Azure HorizonDB lists it as preview. Broadcom said Tanzu for Postgres 18.4 would bundle it (shipping unconfirmed). No official Apache announcement found. — [EDB 1.8.0 notes](https://www.enterprisedb.com/docs/pg_extensions/apache_age/rel_notes/apache_age_1.8.0_rel_notes/), [EDB 1.7.0.1](https://www.enterprisedb.com/docs/pg_extensions/apache_age/rel_notes/apache_age_1.7.0.1_rel_notes/), [Pigsty](https://pigsty.io/ext/e/age/), [Azure GA notice](https://mc.merill.net/message/AZ491161), [Broadcom](https://knowledge.broadcom.com/external/article/442082/apache-age-extension-availability-in-vmw.html)
- [DOC] Kuzu: Apple agreed to acquire Kuzu Inc (Oct 2025, reported via EU records); GitHub repo archived/read-only, last release v0.11.3; site down. Successor/forks (LadybugDB, ArcadeDB/FalkorDB migration guides) exist; LadybugDB claim unverified. — [The Register](https://www.theregister.com/2025/10/14/kuzudb_abandoned/), [BetaKit](https://betakit.com/apple-strikes-deal-to-acquire-canadian-database-software-startup-kuzu/), [MacRumors](https://www.macrumors.com/2026/02/11/apple-acquires-new-database-app/)
- [DOC] PostgreSQL SQL/PGQ (GRAPH_TABLE, CREATE PROPERTY GRAPH) was committed to master on 2026-03-16; so not in PG 18, likely PG 19 (target version unconfirmed). — [pgsql-committers](https://www.postgresql.org/message-id/E1w247I-0000Tk-2Y%40gemulon.postgresql.org), [EDB blog](https://enterprisedb.com/blog/representing-graphs-postgresql-sqlpgq)
- [DOC] Neo4j Community Edition is GPLv3; Enterprise requires a commercial license for closed-source applications (free development/startup programs exist). Clustering is the main Community gap (secondary sources; confirm on neo4j.com). Some secondary sources claim AGPL for Enterprise and conflict with Neo4j's statements; disregarded. — [Neo4j licensing](https://neo4j.com/licensing/?ref=blog), [open-core announcement](https://neo4j.com/blog/open-core-licensing-model-neo4j-enterprise-edition/)
- [DOC] PostgreSQL supports SEARCH and CYCLE clauses for recursive CTEs (since PG 14); CYCLE is rewritten to a path-tracking UNION ALL form; recursive term must be a plain SELECT. — [PostgreSQL commit](https://forger.sitiv.fr/open-dsi/postgres/commit/3696a600e2292d43c00949ddf0352e4ebb487e5b), [vb-consulting](https://vb-consulting.github.io/blog/recursion-postgresql/part3-cycle-detection)
- [VENDOR/anecdotal, weak] Benchmarks are scarce and conflicting. One write-up reports a 6-hop indexed recursive CTE on a 200K-node graph under 2 ms on PG 16 (own tests; row growth under UNION ALL is the real cost driver). A vendor-style comparison claims Neo4j 5-hop ~2 ms vs ~45 ms for recursive CTE (no methodology). A cash-management case study reports Neo4j p99 89 ms vs PostgreSQL multi-table joins p99 3.8 s (joins, not recursive CTE; thin method). One team moved Neo4j to Postgres because queries were mostly 2-4 hops. — [Postgres-as-graph post](https://landing-page-3tt.pages.dev/blog/postgres-as-a-graph-database/), [PuppyGraph](https://www.puppygraph.com/learn/postgres-vs-neo4j), [C# Corner](https://www.c-sharpcorner.com/article/how-we-benchmarked-graph-vs-non-graph-for-cash-management/), [Unoplat](https://unoplat-blogs.pages.dev/blog/neo4j-to-postgres-knowledge-graph-migration)
- [DOC] No published benchmark found comparing UNION vs UNION ALL or CYCLE vs path arrays at million-edge scale. — [search result set above](https://vb-consulting.github.io/blog/recursion-postgresql/part3-cycle-detection)

### Inferences
- [INFER] UKG tenant scale (no source found): a single tenant's configuration (pay rules, pay codes, accrual policies, work rules, schedules, labour categories, integrations, mappings) plus requirements, tests and defects is plausibly 10^3 to 10^5 nodes and 10^4 to 10^6 edges; org-hierarchy/employee-level data is deliberately out of scope (and synthetic-only). Treat as an assumption to validate with a real export; multi-tenant total is a sum of these, partitioned by tenant_id.
- [INFER] At that scale, the cited benchmark conditions (200K nodes, 6 hops, indexed, PG 16) are the same order of magnitude, but do not generalise: impact traversal is typed, filtered, and bounded in depth, which helps; hub nodes (e.g. one pay code referenced by thousands of rules) cause row blow-up under UNION ALL, so use CYCLE/visited-set and test on a hub-heavy synthetic graph.
- [INFER] Recommended choice: PostgreSQL adjacency tables. Reasons: one transactional store with provenance/review tables (FK integrity between edge and evidence rows), tenant isolation via tenant_id (and optionally row-level security), trivial to test with a container, no extra licence. Dedicated DB cost: dual-write consistency with provenance tables, extra ops, licensing (Neo4j GPL/commercial), project risk (Kuzu archived; AGE version-pinned to PG releases, PG 18 only for 1.8.0, and Cypher-in-SQL hampers typed constraints and review tooling).
- [INFER] Determinism: recursive CTE results must be ordered explicitly (ORDER BY path/ids), edge-type filters must be data (an allow-list table), and the traversal must be pure function of (snapshot_id, change_set, rules_version). An in-memory Python graph (rustworkx/NetworkX) loaded from a snapshot is a good second implementation for cross-checking the SQL traversal (differential testing).
- [INFER] ltree suits trees (org hierarchy), not general DAGs with cycles; use it only for hierarchy-path queries. SQL/PGQ is a candidate to revisit once the PG version that ships it is GA and available on the chosen host.
- [INFER] Revisit a dedicated graph DB only if measured p95 impact queries exceed target at real scale, or if users need free-form graph exploration at depth >6 across >10^6 edges.

### Gaps
- No credible, methodologically transparent benchmark of recursive CTE vs graph DB at 10^5 to 10^6 edges found; Memgraph, ArangoDB and Neptune were not researched (time budget); Neptune is AWS-only and ArangoDB/Memgraph have their own licences (unverified here).
- No source for real UKG tenant graph size.
- Neo4j Community clustering limit not verified on an official technical page.

## 3. Change-impact analysis techniques and validation

### Takeaway
Treat impact as typed-edge reachability over a snapshot graph, reported in tiers (confirmed path, possible path via INFERRED edges, unknown/unmodelled), never as a single score. Literature shows that static and dynamic methods each have both precision and recall problems, so independent validation against real outcomes is essential. Commercial tools (LiveCompare, Panaya) add usage weighting, which this product probably cannot get from documents.

### Cited Findings
- [RESEARCH] Impact analysis is traditionally static, dynamic, or combined; precision = |EIS ∩ AIS| / |EIS|, recall = |EIS ∩ AIS| / |AIS| (estimated vs actual impact set). — [ICSE'12 impact analysis paper](https://www.cs.wm.edu/~denys/pubs/ICSE12-ImpactAnalysis.pdf)
- [RESEARCH] A study of dynamic CIA with random changes found even the most cost-effective technique had average precision 38-50% and recall 50-56%; precision often high with recall low or vice versa. — [Buffalo study](https://researchconnect.buffalo.edu/en/publications/a-comprehensive-study-of-the-predictive-accuracy-of-dynamic-chang/)
- [RESEARCH] A comparative study of static CIA techniques found combining two static techniques can improve precision and recall over either alone. — [comparative study](https://www.bohrium.com/paper-details/static-change-impact-analysis-techniques-a-comparative-study/814604185264717824-2502)
- [RESEARCH] A 2008-2018 traceability literature survey found no single technique met all criteria for effective impact analysis; hybrids proposed. Ground truth in code studies is often version-history commits (actual impact sets). — [survey (via search)](https://www.ijitee.org/wp-content/uploads/papers/v8i8/H6388068819.pdf), [STVR 2012 survey](https://typeset.io/pdf/a-survey-of-code-based-change-impact-analysis-techniques-54abmu8whg.pdf)
- [DOC/VENDOR] Tricentis LiveCompare Smart Impact: pipeline with analysis, comparison and usage systems plus an external list of business-critical objects; each object gets Most-at-risk / Impacted / Not Impacted; risk based on depth of impact and frequency of use (needs performance-history usage data). Claims of 84-85% scope reduction and Forrester-commissioned 80% effort reduction are vendor claims. — [LiveCompare 2026.1 docs](https://docs.tricentis.com/livecompare-2026.1/content/smart_impact_learning_app.htm), [Tricentis page](https://www.tricentis.com/products/impact-analysis-livecompare)
- [VENDOR] Panaya extracts custom code and usage logs, statically analyses links between standard and custom objects, and scores "impact likelihood" using usage and test coverage; no independent accuracy benchmark or full scoring method found. — [Panaya docs](https://success.panaya.com/docs/how-to-analyze-impact-and-risk.md), [Panaya PDF](https://www.panaya.com/wp-content/uploads/2018/07/Panaya_ERP_Impact-Analysis.pdf)
- [DOC] Jama/Polarion suspect-link mechanism is a human-cleared "possibly affected" flag (see Q1). — [Jama](https://www.jamasoftware.com/blog/5-ways-jama-connect-makes-traceability-easy/)

### Inferences
- [INFER] Algorithm: forward reachability from the changed node(s) over an edge-type allow-list, each edge type with a propagation rule (e.g. "pay_rule -> uses -> pay_code" propagates; "test_scenario -> covers -> rule" is a reverse lookup to find tests). Output per impacted node: shortest path, all-edges-confirmed flag, path status = min over edges (CONFIRMED > OBSERVED > INFERRED), weakest-edge confidence = min of edge confidences, hop count, evidence ids. Tiers: (A) all edges CONFIRMED/OBSERVED; (B) at least one INFERRED edge; (C) unknown/unmodelled: nodes of types or boundaries with no extractor coverage (e.g. a mapped integration whose target config was not provided). Do not multiply confidences into a probability (edges are not independent, scores are uncalibrated); weakest-edge is simple, explainable, deterministic.
- [INFER] Drift detection: schema-aware diff keyed on stable entity keys between two snapshots (added/removed/changed attribute with before/after values and evidence), as the seed set for impact. Diff on keys, not on file text.
- [INFER] Validation: (1) golden synthetic datasets with hand-authored expected impact sets, checked for exact equality (determinism and snapshot tests); (2) mutation-style tests: delete/alter an edge or node in a graph and assert the impact set changes as predicted (recall check), add decoy edges of non-propagating types (precision check); (3) differential testing SQL vs in-memory implementation; (4) property tests: idempotence, order-independence of ingestion, no cycles non-termination; (5) where real data is ever legitimately available, compare against actual parallel-pay/regression outcomes using precision/recall as above (no source gives such results for UKG; do not claim numbers).
- [INFER] Usage-weighting (LiveCompare/Panaya) is not available from documents; do not imitate "risk" scores without usage data. Present coverage gaps (rules with no covering test, no test result) as facts, not risk percentages.

- No literature found specifically on impact analysis for HR/WFM configuration; transfer from software CIA is inference.

## 4. Information needed for the synthetic overtime-threshold 40 -> 37.5 scenario

### Takeaway
(Synthetic scenario; not a verified UKG rule.) Documents can show *where* a threshold is declared and *what references it* (candidate impact set), but not *how the engine evaluates it* at runtime. Static graph reachability gives a superset of candidates with provenance; only simulation or parallel-pay comparison gives actual pay deltas.

### Cited Findings
- [RESEARCH] Static/dynamic CIA both produce imprecise results (precision 38-50%, recall 50-56% for dynamic in one study), supporting the need for explicit uncertainty and independent validation. — [Buffalo study](https://researchconnect.buffalo.edu/en/publications/a-comprehensive-study-of-the-predictive-accuracy-of-dynamic-chang/)
- [VENDOR] Commercial impact tools rely on usage data and test coverage in addition to static dependencies. — [Panaya](https://success.panaya.com/docs/how-to-analyze-impact-and-risk.md), [LiveCompare](https://docs.tricentis.com/livecompare-2026.1/content/smart_impact_learning_app.htm)

### Inferences
- [INFER] Entity types needed: the threshold parameter/rule (value, unit, period definition, effective dates), the rule container (generic "overtime rule"), things that reference it (pay code, rounding rule, other rules that chain on it), assignment targets (which employee groups/work rules/org nodes it applies to, via assignment tables), accrual/premium interactions, downstream integrations and source-to-target mappings (payroll export fields, hours buckets), requirements citing 40, test scenarios and expected results with hard-coded 40 values, historical defects touching the rule, and environment snapshots (is the value the same in each environment).
- [INFER] Relationship types: DEFINES_VALUE, REFERENCES, APPLIES_TO (assignment), FEEDS (mapping/integration), COVERS (test->rule), VERIFIES_REQUIREMENT, DERIVED_FROM (source evidence), OCCURS_IN (environment snapshot), AFFECTED_BY (defect).
- [INFER] Cannot be known from documents alone: engine evaluation order and precedence between competing rules; how the period boundary (workweek start, pay period vs week) and unit (hours vs decimal minutes) and rounding are applied; interaction with daily overtime, holidays, accrual caps, retro-adjustments; effective-dating behaviour on partially processed periods; runtime assignment (which employees actually hit it); data-dependent paths; hard-coded values in downstream payroll code not exported; statutory/union constraints (a legal check, not a data check); the actual money/hours delta. These need rule-engine simulation, a non-production tenant, or parallel-pay comparison. Product semantics must follow the repo's `ukg-domain-guardrails` (Pro WFM vs Workforce Central differ).
- [INFER] Report format: "candidate impact set from static references" plus "not determinable from artefacts" list plus recommended validation actions; never output pay-delta numbers.

- No UKG-specific documentation was consulted (out of scope/no access); all rule semantics above are generic.

## 5. Deterministic extraction vs NLP/LLM extraction

### Takeaway
Structured artefacts with explicit identifiers (spreadsheet ID columns, XML/JSON exports) can yield OBSERVED edges deterministically; prose requirements, design docs and defect text need LLM/NLP extraction yielding INFERRED edges that require human confirmation. Research indicates LLMs over-predict relations, which supports never auto-promoting.

### Cited Findings
- [RESEARCH] DEPTH (arXiv 2508.14391, v2 Feb 2026): LLMs invent relations for entity pairs with no relation; Qwen2.5-14B-Instruct predicted a relation in 96.9% of no-relation instances on SciERC; the proposed method reduced average hallucination rate to 7.9% and raised micro-F1 by 9.3% across eight benchmarks (benchmark datasets are largely scientific/general, not enterprise config). — [arXiv 2508.14391](https://arxiv.org/pdf/2508.14391)
- [RESEARCH] LLM triplet extraction from financial reports (arXiv 2602.11886) evaluates schema adherence and proposes regex plus LLM-judge faithfulness checks without ground truth. — [arXiv 2602.11886](https://arxiv.org/pdf/2602.11886)
- [RESEARCH] Hallucinated synthetic training data degrades relation-extraction models; automatic detection tested. — [arXiv 2410.08393](https://arxiv.org/abs/2410.08393)
- [RESEARCH] TraceLLM (arXiv 2602.01253): LLM requirements-traceability results are sensitive to prompting; domain/role context and explicit artefact-relationship description raise precision without recall loss; over-prediction of links without domain context; random example selection can degrade below zero-shot. Traceability work uses F2 (recall-weighted) because tools assist analysts. — [TraceLLM](https://arxiv.org/pdf/2602.01253)
- [RESEARCH] KIT study: LLM-ensemble candidate filtering achieved F2 comparable to IR methods but lagged in precision. A cross-task RE evaluation did not report recall because no complete ground-truth links exist (arXiv 2608.21531). — [AIRE25 KIT study](https://fuchss.org/conferences/aire25/), [arXiv 2608.21531](https://arxiv.org/pdf/2608.21531)

### Inferences
- [INFER] Deterministic, OBSERVED-grade: explicit foreign-key-like ID references in spreadsheets (e.g. "Requirement ID" column on a test case sheet, "Mapping ID", rule-name references in config exports), XML/JSON parent-child and reference attributes, source-to-target mapping rows (source field, target field, transform), test result rows keyed to test IDs, defect IDs linked to test IDs in exports. Caveat: observed means "the source states it", not "semantically correct"; validate IDs resolve (dangling references become a data-quality finding).
- [INFER] Rule-based INFERRED (high precision, not certain): exact-name string matches of config entity names in requirement text, ID patterns inside prose (e.g. "REQ-123" in a defect description), table-of-contents or section-number cross references. Store the matching rule id and span.
- [INFER] LLM-assisted INFERRED only: requirement-to-config links from prose, implied dependencies in design docs, defect root cause attributions, intent of a mapping. Constraints: ontology-constrained output (closed edge-type list), mandatory evidence quote with offsets verified by code (string must exist in the source, otherwise reject), model/prompt version recorded, confidence stored as uncalibrated, status capped at INFERRED, human review queue to reach CONFIRMED. Evaluate with recall-oriented metrics (F2) plus a precision audit on a hand-labelled sample, because the cited work shows over-prediction.
- [INFER] Do not extrapolate the 96.9% figure to this domain: it is one model on one scientific benchmark; measure on our own synthetic labelled set.
